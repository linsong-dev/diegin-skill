## 摘要（3 分钟版）

当代 AI Agent 有一个系统性缺陷：**同样的问题会反复出现**。解决它需要的不是一个更聪明的 Prompt，而是一个**常驻的进化层**——在每次会话、每次工具调用背后持续运行：检测错误、固化修复、沉淀成功、跨域泛化、验证真伪。

迭进（Diegin）以 **律令九章** 实现这一进化层（四律三门一锁一镜；九章按演化顺序排列，攻七开篇、自照镜终章）：

| 章 | 原则 | 别名 | 方向 | 一句话 |
|:-:|:--|:--|:--|:--|
| 一 | 攻七 | 行知律 | 正向强化 | 试之以行 → 成则炼之 → 通则固之 → 泛而验之 → 废则舍之 |
| 二 | 守三 | 省知律 | 负向纠错 | 失则拆之 → 拆则溯之 → 溯则炼之 → 炼则铭之 → 铭则复战 |
| 三 | 一二不过三 | 三错锁 | 安全阀 | 初犯立改验 → 再犯锁其途 → 三犯剑落下 |
| 四 | 举一反三 | 通变门 | 跨域泛化 | 一法通 → 三法生 → 百法衍 → 验而归真 |

## 一、问题：AI 为什么总重复犯错

### 1.1 现象

在使用 AI Agent 完成真实工程任务时，以下场景反复出现：

1. **同样的错误隔几天再来一次**：同一个编码问题（如文件编码、转义、路径）在不同的会话中重复踩坑；
2. **修好了这次，下次从零开始**：即使本轮修复成功，方法没有沉淀，下一轮 AI 又回到「从头试错」；
3. **成功经验不沉淀**：偶然用对了的方法没有被识别、固化，下次可能又用错的方式；
4. **规则写了却像假的**：规则存在但从不触发（本系统曾实测 215 条 active 规则中 202 条从未触发）。

### 1.2 根因

这不是模型能力问题，而是**系统结构问题**：

- **无状态**：会话结束后，行为经验随之消失；
- **无负向闭环**：错误发生后缺少「检测 → 归因 → 固化 → 验证」的自动链路；
- **无正向闭环**：成功只是偶然，不构成可复用的知识资产；
- **无验证**：即使写入了规则/记忆，也没有机制证明「它真的会生效」。

### 1.3 为什么值得解决

AI Agent 进入生产环境的瓶颈，已经从「能不能做」转向「**可不可信**」。重复犯错直接打击信任；而信任一旦被「同一个错犯两次」破坏，再强的能力也难以挽回。进化层解决的不是单次任务的成败，而是**长期可靠性**。

## 二、现有方案的局限

| 方案 | 本质 | 解决什么 | 局限 |
|:--|:--|:--|:--|
| LOOP 类循环（Reflexion 等） | 单轮「执行→反馈→反思→再执行」模板 | 这一次怎么做好 | 循环结束经验即散；只反思失败，很少固化成功；无仲裁、无调度 |
| Codex 目标模式（goals） | 平台级任务管理 | 任务怎么推进、续跑 | 不沉淀成功经验；失败处理由平台控制，无认知层 |
| 向量记忆库 / RAG | 外部知识存取 | 信息检索 | 检索不等于行为约束；不会主动拦截错误、固化规则 |
| Prompt 模板 / 系统提示词 | 指令注入 | 一次性行为约束 | 静态、无状态、不可自举进化 |

**定位一句话**：

> 目标模式 = 导航（要去哪）；LOOP = 驾驶动作（怎么开）；迭进 = 车载进化系统（越开越稳、越开越聪明、错不重犯）。

迭进与前三者不冲突：它可以运行在目标模式之上，容纳 LOOP 作为执行循环之一，并以语义记忆作为知识底座。

## 三、方法论：律令九章

### 3.0 总览：网络而非步骤

九条原则不是顺序执行的流水线，而是**互联的网络**：每条原则有职责、触发时机、闭环出口，通过「预策（裁决律）」与「去伪存真」与其他节点互联。整体数据流：

```text
用户消息/事件 → [恒常门] 入口恢复检查（未完成任务→恢复前用户确认；生成 task_id）
         → [预策·汇] 汇集原则输出 + 状态摘要 + task_id
         → [去伪存真] 验证信息真实性
         → [守三·轻量] 扫描失败模式
         → 执行操作
            ├─ 成功 → [攻七] 提炼成功模式
            └─ 失败 → [一二不过三] 立改→加固→升级
         → [预策·衡/策] 按 P0-P6 裁决（P6 语义记忆权重 ±0.3/单轮±0.1）
         → [止观] 封存本轮（四态 + 只读快照）
         → [守三·深度] 离线复盘
         → [自照镜] 照见方向（每10轮或每日；勇气信号 ×0.6 半衰期）
```

### 3.1 守三（负向纠错）

> 拆解自己 → 找出不足 → 对比提炼 → 总结改进 → 写入固化 → 触发执行

- **轻量自检**：每次操作前扫描最近失败模式（常驻钩子，微秒级）；
- **深度复盘**：每日/每 10 轮操作后系统性回顾 strike 日志；
- **应急触发**：一二不过三在连续 3 轮内触发 ≥2 次阻断时，立即强制执行一轮深度复盘，不等定时周期；
- **锚定优先级**：对比期望行为时，优先检索 success_patterns 中同场景高置信度模式（≥4.0），无则回退「原始用户意图（intent_summary）」；
- **闭环**：写入固化 → 触发下一轮。

### 3.2 攻七（正向强化）

> 识别优势 → 复盘成功 → 提炼模式 → 主动写入 → 验证效果 → 迭代微调

- 成功案例发生后**立即触发**；
- v3.8 强化四条链路：及时推荐（conf≥4.5 标 priority）→ 优先选用（仲裁 P4 同场景加权 +0.5）→ 泛化提速（复用≥2 次或 conf≥4.5 即跨域）→ 反馈闭环（自动采纳 +0.5 / 否决 ×0.7）。

### 3.3 一二不过三（三错锁）

> ①错立改+改毕验 → ②再错加固阻断 → ③三错升级处理

- 第 1 次：立即自动修复并验证；
- 第 2 次：去伪存真归因 → 内生惯性写入硬阻断；
- 第 3 次：推翻原阻断方案、通知用户、系统升级。
- **警觉不阻断**：第 1 次与第 2 次之间保持警觉但不影响正常操作——预策权衡时将该操作风险权重上调一档，或相关模式置信度 -0.2，不触发阻断；
- **实证**：`view_image` 在 2026-08-10 某会话内连发，累计第 3 次触发升级，`self_error_image_url` 从 archived 复活为 critical，当日 11 次命中全部走审计（熔断期行为），按计划复查无复发即可人工 reset。

### 3.4 举一反三（跨域泛化）

> 举一 → 反三 → 通百 → 回归校验

- 从一条经验推导跨域通则（如「编码规则」从代码域泛化到写作/数据分析域）；
- 泛化产物先进 **staging**，经去伪存真验证后才激活（P5 规则不参与实时仲裁）；
- **语义阈值**：跨场景候选规则之间须满足语义距离阈值（向量余弦相似度 <0.7），否则判定为「伪泛化」，不进入 staging；
- **实证**：08-09 入库的 2 条跨域泛化规则，08-10 实战触发 71/74 次、零误伤，人工复核保留发布。

### 3.5 去伪存真（真伪门）

> 言必有证 → 证必可验 → 验证为真

- 所有规则、模式、记忆在**生效前**经过验证；
- 写入门禁：trigger 引用不存在的字段 → 拒绝写入（P0 确定性死规则）；
- 周期审查：active 超 7 天从未触发的规则 → 死规则候选，进入分级处置（修复/保留/归档/删除）；
- **暂存保留期**：pending 条目 50 轮/7 天（先到者）自动淘汰，外部新证据可重置一次；
- 证据有效性门：evidence_filter 不再写假 pass；季度证伪；
- **关键原则：验证必须用「运行证据」，不用「代码存在」代替**——`triggered_count > 0` + 审计 BLOCK 记录才算生效。

### 3.6 预策（裁决律 · 优先级宪法）

当原则冲突时，硬编码裁决，不可逾越。预策律不产生规则，只提供优先级排序；所有原则的输出最终汇聚到仲裁器，按上表裁决：

| 优先级 | 规则 |
|:-----:|:----|
| P0 | 去伪存真无条件优先（假信息不入任何流程） |
| P1 | 一二不过三阻断优先于攻七/举一反三（安全阀高于强化泛化） |
| P2 | 止观「事毕清零」优先于守三延伸纠错 |
| P3 | 恒常门任务恢复优先（恢复信号在「衡」中统一决策；恢复前须用户确认） |
| P4 | 守三 vs 攻七冲突 → 置信度裁决（含 P6 语义记忆权重；delta≤0.1 守三优先） |
| P5 | staging 规则不参与实时仲裁 |
| P6 | Mindol 语义记忆权重（高分历史经验双向调节规则/模式置信度，调权范围 ±0.3、单轮影响 ≤±0.1；仅影响 P4 与兜底，不凌驾 P0-P3） |

预策六步：**汇**（汇集各原则输出 + 任务恢复状态 + task_id）→ **衡**（统摄权衡，含 P0-P6 硬优先级 + 语义记忆）→ **预**（谋划推演；**主动推进检查**：连续 3 轮入口检查均无用户输入、无待恢复任务且 staging 非空时，主动验证候选规则；无 staging 则静默等待，不制造伪任务）→ **策**（拍板策动）→ **行**（执行操作）→ **复**（执行后新冲突信号再入权衡）。

### 3.7 恒常门（持存 · 任务续接）

> 启而探之 → 行而记之 → 断而存之 → 续而接之

- **入口恢复检查**：每次入口检索 Mindol codex 中未完成任务（status≠completed 且未超时）→ 恢复前向用户确认（摘要 ≤50 字）；生成/沿用 task_id；
- **状态追踪**：任务执行中维护 task_id 与状态；中断/切换时生成状态摘要（含完成标准、阻塞报告）；
- **封存包**：保留 30 天，超时自动清理；父任务关联 parent_task_id，嵌套深度 ≤3 层；已完成任务永不自动恢复；
- **状态四态**：未完成 paused、完成 completed、用户放弃 abandoned、子任务受阻 blocked（含 blocker_report）；
- **运行版兼容**：缓急律（pacemaker）已从九章移除，降级为宕机时段/批处理的节奏工具（23:00-06:00 宕机分流 + cron 批处理仍由其承载），不占据 P3 优先级。

### 3.8 止观（完形律 · 完形封存）

> 事毕则封 → 功过即舍 → 心如明镜

- 每轮结束：打包经验 → 卸载工作内存 → 归档长期记忆；
- 封存后不再追加纠错/强化，除非同一事项在新上下文重新出现；
- **状态四态**：未完成 paused、完成 completed、用户放弃 abandoned、子任务受阻 blocked（含 blocker_report）；
- **只读快照**：为守三应急复盘保留执行轨迹只读快照（含阻断记录、工具调用序列、裁决日志摘要），仅用于根因分析，不修改任务状态；
- **封存后只读豁免权**：事后根因分析产出独立新规则入库，不回溯修改已封存任务的 status/completion_criteria，故不视为「追加纠错/强化」；
- 与恒常门配合传递封存包；与缓急律（pacemaker）配合设置宕机时段，形成「张弛有度」的节律。

### 3.9 自照镜（方向之镜 · 自我审视）

> 回望所行 → 静照本心 → 拨云见路 → 辨繁识简 → 笃定前行

- **时机**：完形律封存本轮后 + 守三深度复盘结束后（跟随守三频率触发，默认每 10 轮或每日；守三复盘未触发时静默跳过）；
- **审视**：执行模式是否冗余重复？是否偏离初心？是否简洁高效？是否因主动冒险而获得超额收益？
- **勇气信号**：如有超额收益，生成勇气信号经 P6 语义记忆正面加权，对冲纠偏偏好；半衰期式衰减：每轮剩余 ×0.6（约每 2 轮减半），3 轮后约剩 10%、5 轮后不足 1%（注：定稿文字为约数，按×0.5估算；实现按公式每轮×0.6：3轮≈21.6%、5轮≈7.8%，以公式为准），自然归零；
- **约束**：只生成报告与方向信号，不产生规则；不参与实时仲裁；照见结论为建议而非指令，不凌驾预策律 P0-P3 硬优先级。

## 四、系统架构：进化层的工程形态

迭进不是论文概念，而是可运行的工程系统，四层构成：

```text
┌────────────────────────────────────────────────┐
│ 接入层：平台钩子（常驻、全域）                   │
│   Codex: PreToolUse/PostToolUse/SessionStart/  │
│          UserPromptSubmit/Stop                 │
│   Claude Code: PreToolUse/PostToolUse/         │
│          SessionStart/UserPromptSubmit/Stop    │（适配器，M2）
├────────────────────────────────────────────────┤
│ 契约层：钩子契约 v1（统一信封，平台无关）        │
│   5 标准事件 + 三态决策 + inject/suggestions    │
├────────────────────────────────────────────────┤
│ 引擎层：律令九章引擎                            │
│   规则引擎 / 仲裁器 / 追踪器 / 恒常门 / 完形律   │
│   / 自照镜 / 证据库 / 错误检测 / 健康仪表盘      │
├────────────────────────────────────────────────┤
│ 记忆层：Mindol 语义记忆                        │
│   内存检索 ~2ms / SQLite 仅持久化 / 零外部 API  │
└────────────────────────────────────────────────┘
```

### 4.1 接入层（常驻钩子）

进化层必须**常驻**：不是用户想起来才跑，而是在每次工具调用前、每次回复前、每轮结束自动执行。迭进通过平台钩子系统实现（Codex 全 5 钩子已接入契约通道；Claude Code 适配器 v1 已交付源码库，端到端待真实环境实测）。

### 4.2 契约层（平台无关）

《迭进钩子契约 v1》定义了平台无关的统一信封：任意智能体只要具备钩子系统，即可通过薄适配器接入迭进，无需改动引擎。这使进化层从「Codex 专用」走向「智能体通用」。

### 4.3 引擎层（律令九章）

引擎以规则库 + 模式库为血肉，运行时按预策律（裁决律）仲裁：入口经恒常门做任务恢复检查，收尾经止观封存、自照镜做方向校准。质量护栏：
- `audit_patterns` / `audit_staging` / `audit_evidence` 防空壳模式与假数据再生；
- 自检 14 项（死规则/恒真规则/双库一致/编码/证据有效性/基线回归等）；
- 守护协议三环六步（分析→审查→验证），写入门禁 + 周期审查 + 触发验证。

### 4.4 记忆层（Mindol）

## 六、边界与诚实声明

1. **不夸大**：迭进提升「长期可靠性」，不承诺「永不犯错」；它让错误被检测、被固化、不再重犯；
2. **fail-open 纪律**：引擎/契约异常时一律放行业务（标注未验证），不因进化层故障阻断用户工作；
3. **验证优先**：本文所有数据可复现；「代码存在 ≠ 生效」，一切以运行证据为准；
4. **平台绑定现状**：Codex 全钩子已接入；Claude Code 适配器已交付源码库（端到端待真实环境实测）；其余平台按契约路线图推进；
5. **适用边界**：规则引擎对结构化/半结构化任务收益最大；纯开放创作场景仍需人工裁决。
